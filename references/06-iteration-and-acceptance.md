## 官方推进顺序

1. **最小可玩版本**：能开始、能操作、能结束、能重开。
2. **修阻断流程问题**：卡死、按钮点不到、状态不重置、必现崩溃。
3. **调节奏、数值、手感**：难度曲线、生成间隔、移动加速度、反馈强度。
4. **补素材、音效、引导、发布物料**：最后再做，避免美术返工。

门槛：上一级没验收通过，不要开下一级。尤其不要用「加音效」掩盖「玩法闭环没通」。

## 四段式需求

每条需求四段，缺一段就容易返工：

| 段落 | 写什么 | 反例 |
|---|---|---|
| 目标 | 这一轮只解决什么 | 「优化体验」 |
| 现状 | 现在实际是什么表现 | 「感觉不太对」 |
| 约束 | 必须保留 / 不要改的部分 | 不写，结果 AI 顺手重构了别的 |
| 验收 | 怎样算完成，可观察 | 「更好玩」 |

示例：

~~~text
目标：让角色拖动更跟手。
现状：手指移动约 0.2 秒后角色才开始动，松手后还会滑一小段。
约束：保留现有操作区域（屏幕下半区）、现有碰撞判定、Astroon 主题不要改。
验收：拖动与手指同步、松手立刻停；正常速度下不出现穿模；重开后行为一致。
~~~

写作要点：

- 「现状」用现象描述，不带评价（「点了没反应」优于「按钮很烂」）。
- 「约束」越具体越好：哪些文件/界面/参数不能动。
- 「验收」尽量能被第三方复现。

## 一次只聚焦一个结果

一条需求只允许一个主结果。出现「并且 / 同时 / 顺便」时，拆成两条。

- 好：「把失败判定从碰到中心改成碰到边缘」
- 差：「改失败判定，顺便加音效、把背景换成夜空、难度再低一点」

原因：一次改多处，出问题时无法定位是哪一处引起的，回滚也会连带丢改动。

## 要求 AI 自证

每轮需求末尾加一句：

> 改完后请自行构建、检查错误，并说明：改了什么、怎么验证的、验证结果如何、有没有已知遗留问题。

复杂改动再加一句：先给一个简短计划（分几步、动哪些文件），我确认后再改。

## 报 bug 的五件事

| 要素 | 示例 |
|---|---|
| 设备 / 页面 | iPhone 17 预览、游戏页 |
| 操作步骤 | 开始游戏后连续快速左右拖动 3 次 |
| 实际现象 | 角色卡在屏幕左边缘不动 |
| 期望现象 | 角色应跟随手指 |
| 能否复现 | 每局都能复现 / 只出现一次 |

有截图或录屏就附上；能定位到具体界面与按钮更好。

## 常见迭代类型

| 类型 | 典型条目 |
|---|---|
| 手感 | 输入延迟、加速度、惯性、碰撞反馈、顿帧、屏幕震动 |
| 数值 | 难度曲线、生成间隔、得分倍率、生命值、道具时长 |
| 节奏 | 波次间隔、紧张—松弛、休息点、失败后重开速度 |
| 引导 | 首屏说明、首次操作提示、失败原因提示、目标提示 |
| 视听 | 音效触发点、BGM 切换、按钮反馈、受击特效 |
| 健壮性 | 后台切回、网络断开、暂停恢复、重复点击 |

## 预览五项验收

官方清单，逐项记录「通过 / 不通过 + 证据」：

| # | 检查项 | 通过标准 |
|---|---|---|
| 1 | 能否正常开始 | 打开预览点开始即进入游戏，无报错、无白屏 |
| 2 | 操作是否符合预期 | 每个操作有响应，触控区域正确，按钮可点 |
| 3 | 成功 / 失败 / 重开是否完整 | 胜负都能触发，结束页信息正确，重开状态清零 |
| 4 | 画面在目标设备是否清楚 | 目标机型上字号可读、对比足够、不被开孔/刘海遮挡 |
| 5 | 有无卡住流程的问题 | 不存在点了没反应、黑屏、卡在加载、无法退出的路径 |

设备模拟：PC / 手机 / 平板二级菜单；手机含默认、标准全面屏、iPhone 17（402×874，会显示灵动岛遮罩并阻挡该区域点击）。

## 发布前 6 项健康检查

1. 完整走一遍核心流程（从进入到重开）。
2. 边界状态：失败、胜利、暂停、恢复都正常。
3. 目标方向（横/竖屏）下界面完整可用。
4. 实机验证：三类存档、网络容器相关按钮可用。
5. 物料与当前版本一致（截图不是旧版本）。
6. 没有已知的阻断性问题。

## 数据检查 6 条

运行环境分三种：**预览**（项目内直接预览）、**测试**（分享页 / 实机测试二维码）、**线上**（TapTap 启动已发布游戏）。常驻服务器、匹配组队、服务端云变量按环境隔离，预览数据不会自动进入测试或线上。

三类存档怎么选：

| 需求 | 用法 |
|---|---|
| 只在本机、离线可用 | 本地存档（File / FileSystem） |
| 随账号、单人、允许客户端提交 | 客户端存档（clientCloud） |
| 联网服务端游戏、防篡改、跨玩家、排行榜、货币/道具交易 | 服务端存档（serverCloud，走服务器校验） |

检查 6 条：

1. 不要把预览里的测试数据当成正式数据。
2. 本地存档要实机验证「退出重进」后还在。
3. 客户端游戏要验证成功、失败、超时三种回调的默认值。
4. 更新测试版后要重新复验关键链路。
5. 小范围真机验证：开始、存档、结算、重开。
6. 服务端逻辑确认幂等与原子；断线重连、重启后能恢复。

实施前让 AI 读项目里最新的存档文档（`file-storage.md`、`client-cloud-score.md`、`server-cloud-score.md`），不要沿用旧日志里的接口。

## 横竖屏切换

1. 通过对话让 AI **同时**改游戏布局与项目方向配置（该配置不在普通页面直接编辑）。
2. 重新构建。
3. 在预览与实机检查按钮、文字、触控区域、安全区。
4. 记录哪些界面需要重新排版（开始页、HUD、结束页最容易漏）。

## 对话管理

- 同目标留在同一对话，AI 有上下文，改动更连贯。
- 换方向（换玩法、换主题、换技术路线）新建对话，避免旧约束互相打架。
- 长对话变慢或跑偏时，先让 AI 总结「当前已确认的设定」，再决定是否新开。

## 常见失败模式

| 失败模式 | 症状 | 对策 |
|---|---|---|
| 需求太大 | AI 只做了一半，且各自都不完整 | 拆成一次一个结果 |
| 验收模糊 | 每轮都说「好了」，但你没感觉变好 | 验收写成可观察现象 |
| 跳步 | 玩法还没闭环就做美术 | 回到官方顺序 |
| 让 AI 猜 | 关键设定前后不一致 | 确认单锁定设定 |
| 改一处崩一处 | 没写「约束」 | 约束里列不可动部分 |
| 只看预览不上真机 | 真机上按钮点不到、字太小 | 阶段 4 必须实机/二维码验证 |
